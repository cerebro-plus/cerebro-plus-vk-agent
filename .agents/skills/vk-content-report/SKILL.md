# Маршрут

1. Получить только подтверждённые выходы `$analyze-vk-best-posts`: `vk_posts_dataset.json`, JSON комментариев, `vk_best_posts.xlsx`, `final_validation.json`, изображения и расшифровки клипов. Брать пути из `posts_handoff.json`, если он есть.
2. Выполнить `prepare` один раз. Остановиться при неверном статусе, хэше, множестве `post_id`, ER, бенчмарке, ссылке, XLSX, медиапути или расшифровке клипа. Требовать, чтобы множество прямых ссылок на посты в XLSX совпало с dataset.
3. Визуально сверить все обязательные листы XLSX и исходные изображения/кадры клипов. Прочитать все расшифровки. JSON использовать как основной источник данных; XLSX — только как контроль происхождения и визуальную сверку. Записать результат в `findings.visual_review`; без полного подтверждения `build` обязан остановиться.
4. Прочитать `outputs/analysis_input.json` и `outputs/comment-signals.json`. Проанализировать все проверенные посты, а не только `is_best`.
5. Создать `findings.json` строго по `references/analysis-contract.md` и `references/report-structure.md`.
6. Выполнить `build`, затем `validate`. Показать пользователю HTML и краткий итог. Попросить явно подтвердить результат.
7. Только после явного подтверждения выполнить `confirm`, повторить `validate`, создать `report_handoff.json` и обновить `chain_manifest.json`.

# Правила анализа

- Рассчитывать `relative_er = er / benchmark` только при валидном ER и `benchmark > 0`.
- Ранжировать все пригодные посты по `relative_er`. Размер каждого квартиля — `ceil(N × 0.25)`.
- Анализировать весь набор, но выбирать доказательства по приоритету: прямые конкуренты, затем косвенные, затем конкуренты за внимание. Не скрывать отсутствие прямых конкурентов.
- Если вывод использует более низкий уровень конкурентов при наличии постов более высокого уровня в доступной выборке раздела, заполнить `tier_escalation_reason` конкретной причиной нехватки релевантных доказательств.
- Разбирать верхний и нижний квартили отдельно: форматы, темы, CTA, реакции и вложения.
- Дополнительно разбирать вопросы аудитории, подтверждённые комментариями триггеры, обещания, аргументы, визуалы, тон, сценарные приёмы и первые секунды клипов.
- Не выдавать текст поста, высокий ER, кодовые слова, эмодзи или короткие реакции за подтверждение интереса либо покупательского триггера.
- Если комментариев нет, прямо писать, что вопросы, содержательная реакция и покупательские мотивы не подтверждены. Не придумывать цитаты из комментариев.
- Приводить постовые цифры ER и бенчмарка только для публикаций с `relative_er >= 2` или `relative_er <= 0.5`. Общие размеры выборки и агрегаты комментариев указывать всегда.
- Использовать точные короткие цитаты CTA, постов, комментариев и расшифровок. Не превышать 200 символов на цитату.
- Для CTA с найденной формулировкой приводить дословную цитату CTA. Если есть содержательные комментарии, приводить хотя бы одну дословную цитату комментария. Для обещаний, аргументов и хуков приводить цитату, когда в доказательствах есть текст или расшифровка.
- Не писать числовые ER, бенчмарки и отношения вручную в `headline`, `analysis` или `summary`. Передавать разрешённые посты только через `metric_post_ids`; HTML подставляет проверенные цифры сам.
- Писать отчёт языком, понятным даже ребёнку: короткими предложениями, без необъяснённого профессионального жаргона и сложных оборотов. Перечисления оформлять списками, а не длинными строками через запятую.
- Не утверждать причинность там, где есть только совпадение с высоким или низким относительным ER.
- Не добавлять рекомендации, советы, контент-план или идеи будущих публикаций.

# Неподвижный HTML-контракт

- Верстать смысловые блоки вертикально.
- Сделать короткий отчёт, который при печати укладывается в 1–2 страницы.
- Перед показом пользователю открыть готовый HTML, проверить читаемость и распечатать его в PDF или открыть предпросмотр печати. Остановиться, если получилось не 1–2 страницы.
- Каждый отдельный аналитический вывод выводить как `<li class="analysis-bullet">`.
- Внутри каждого такого `<li>` размещать ровно один вложенный блок `<div class="post-example">` со строкой `Пост-пример:`.
- В `Пост-пример:` выводить кликабельные прямые ссылки на все `evidence_post_ids` этого буллита. Не выносить ссылки в общий список и не объединять доказательства нескольких буллитов.
- Строить ссылки только как `https://vk.com/wall<post_id>`, открывать в новой вкладке.
- Не создавать аналитические буллиты без поста-примера. Если факт нельзя подтвердить ни одним постом, перенести его в вводный текст без маркированного списка либо удалить.
- Использовать разделы и категории, заданные в `references/report-structure.md`.

# Остановка

- Не начинать анализ при неподтверждённом предыдущем этапе или незавершённом медиагейте.
- Не обращаться к VK API и не выполнять новый поиск конкурентов или постов.
- Блокировать неизвестные `post_id`, неверные прямые ссылки, пустые доказательства, неподтверждённые цитаты и причинные выводы.
- Блокировать HTML, если число аналитических буллитов не равно числу вложенных блоков `Пост-пример`, если внутри хотя бы одного буллита нет ссылки или если ссылка находится вне буллита.
- Не выполнять `confirm` без явного подтверждения пользователя.
